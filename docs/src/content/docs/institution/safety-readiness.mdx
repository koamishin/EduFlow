**Use OpenSinop for evaluation before relying on it for institutional funds.**
This page describes the inspected code, not a financial audit or a promise of deployment
readiness. Passing tests and a successful testnet transfer are different from proving
that a school can operate the full system safely.

## What exists today?

| Area | What the application includes | Important limit |
| --- | --- | --- |
| Manual collections | Private uploads, exact totals, independent batch review | Staff attestation, not independent bank proof. |
| Department planning | Selected bill sets, cash and allocation checks, plan review | A proposal is not a reservation or permission to pay. |
| Reviewed vendor payments | Drafts, funding windows, holds, reviewer enrollment, durable submission, settlement matching | Testnet only; full operating and concurrency validation is still needed. |
| Recovery | Reviewed capacity release, funding rollover, outbox and attempt records, observation | Do not assume every expired approval or lost provider response has a complete operator recovery flow. |
| Student payments | Quotes, consent, processing, verification, pilot allocations | Operator-controlled test wallets, not a production student custody solution. |
| Policy advice | Policy revisions, examples, publication, evaluations, analytics | Advice and confidence scores are not spend authority or assurance of correctness. |
| Recurring mandates | Preparation, review, occurrence checks and supervision | A recorded release disposition is not itself proof of payment submission. |

## Experimental automatic bridge

This is separate from the ordinary reviewed path. It connects an already verified
student tuition payment to collection review, planning, and a possible vendor payment.

The configuration currently defaults both of these to `true`:

```dotenv
EDUFLOW_AUTONOMOUS_PIPELINE_ENABLED=true
EDUFLOW_AUTONOMOUS_PIPELINE_AUTO_DISBURSE=true
```

The default automatic bill ceiling is `50.00` USDC. This ceiling is not a complete
institutional spending policy or a certification of safety.

### Why a recorded reviewer is not proof of human approval

The bridge can choose staff records, grant reviewer permissions, generate a reviewer
TOTP from stored authenticator material, and supply a hardcoded demo password to the
review action. It also turns submission on in the running process. These behaviors must
not be described as a fresh, independent human payment authorization.

When its verifier reports settlement, the bridge can mirror a transaction and mark the
invoice `paid`. That testnet state must not be treated as proof that a real supplier
received the institution's local-currency payment.

### Where it can run

- The scheduler invokes the bridge every five minutes when its enabled flag is true.
- Reviewing a tuition-linked collection can invoke it.
- **Auto-Verify & Bridge** invokes it directly.
- The command `eduflow:autonomous-pipeline-bridge` invokes it directly.
- Receipt approval from Policy evaluations can invoke it for linked tuition.

The enabled flag gates scheduled and some automatic calls. **It is not checked by
every direct entry point.** The auto-disburse flag is checked later, after earlier
review and planning work may already have happened.

### Safest evaluation boundary

Use an isolated instance with simulated data and no live signing credentials. Set both
bridge flags to `false`, keep submission/student payment runtimes off, and avoid direct
bridge actions and commands. These settings reduce exposure; they do not create a
complete authorization boundary where the code has none.

This documentation change does not repair or enable the payment code. Any production
use needs a separate security and financial review.

## Amounts and settlement evidence

New evidence paths preserve exact amounts, but older treasury and payment paths still
contain floats and two-decimal storage. Do not infer that all historical amounts can
be reconstructed precisely.

A transaction hash alone says nothing about success or payment matching. The dedicated
verifier must match network, asset, economic sender, recipient, exact amount, and
successful movement. A provider timeout or unreadable lookup remains unresolved—not
proof that a payment failed or that someone fabricated evidence.

### Settlement verdicts

The legacy `lepton:reconcile` command and the dedicated payment verifier answer
different questions:

- **Legacy `verified`:** a successful receipt exists for that hash; this does not alone match the expected bill amount and recipient.
- **Dedicated verified settlement:** the expected movement was checked against the payment evidence.
- **Pending / observed / unresolved / unverifiable:** more evidence is needed. Never resend blindly.
- **Reverted:** a readable chain receipt reports failed execution.
- **Simulated:** no network settlement is claimed.

## Deployment limits

The locked Lepton package is `v3.0.0-rc.1`. A prerelease version and application tests
do not certify provider integration, PostgreSQL concurrency, shared rate-limit state,
backup restoration, or failure recovery in a school's environment.

Webhook ingestion is contained behind signature and subscription checks and only queues
observation. A verified notification still does not settle a payment.

The stock Compose setup runs the web service, database, and Redis. It does not supply
a complete background-service or backup strategy. See
[Run background services](../../guides/operations/).

## What a release review still needs

Test the complete configured path: permissions, authentication, exact money, provider
behavior, duplicate requests, worker crashes, unresolved transfers, updates, restore,
and human recovery. Confirm custody, privacy, provider availability, and local legal
requirements separately.

Installation, an approved plan, a policy publication, and a testnet receipt are useful
milestones. None is a certificate for real institutional funds.
