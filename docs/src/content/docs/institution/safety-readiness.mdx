:::caution[Status: blockers identified; hardening is not yet implemented]
OpenSinop and its Lepton dependency require separate release gates. Neither a green test
suite nor a new package tag certifies the application for real institutional funds.
:::

## Current integration blockers

- **Lepton v3 is a prerelease.** The lock file installs `v3.0.0-rc.1`. Pin it, then run
  the application regressions and a separately authorised testnet integration against
  it before any school release; a green suite on an RC is not certification.
- **Legacy exact-money paths remain.** Treasury and payment float APIs and two-decimal
  money columns still exist outside the reviewed evidence path; SQLite floating-point
  money storage is refused rather than presented as exact. Historic values are not
  silently re-derived.
- **Payment lifecycle gaps.** Reservation release/funding rollover, approval
  renewal/withdrawal, reviewer-factor recovery, local-to-testnet mapping authority,
  durable outbox/attempt recovery, execution recovery and matching settlement
  verification are still required.
- **Deployment boundaries are uncertified.** PostgreSQL concurrency, provider races and
  shared-cache login-replay state are not certified; Composer metadata, Docker settings,
  queue/scheduler processes, credentials, authorisation and reconciliation must be
  tested together — package unit tests do not cover those boundaries.
- **Provider and jurisdiction eligibility are not certified.** Self-hosting OpenSinop
  does not make Circle's hosted infrastructure available in every jurisdiction, and an
  on-chain receipt cannot close a custodian or payout-partner obligation.

Webhook ingestion itself is already contained (signature headers, raw-body verification,
type/network allowlists, durable inbox) — see
[Security](/guides/security/#webhook-ingestion).

## Remaining hardening gates

1. **Validate the REST driver.** Correct endpoint paths and request fields against
   official schemas, paginate reads, scope wallets to chain and wallet set, verify API
   access, and document unsupported operations.
2. **Prove exact balances and bounded sends.** Identify USDC by trusted token and chain
   identity, normalise to six-decimal base units with exact arithmetic, never add Arc's
   native and ERC-20 views of the same balance. Enforce approved amount, recipient,
   network and fee controls at the signing boundary; an estimate is not an enforceable
   fee ceiling.
3. **Recover without duplicate payments.** Persist submission identity and a
   provider-compatible idempotency key before sending; record webhook events in a durable
   inbox with unique `notificationId`; queue bounded reconciliation. Duplicate and
   out-of-order notifications must not regress state or cause another transfer.
4. **Verify settlement independently.** Notification delivery, a provider ID, `CONFIRMED`
   or a stored hash alone must never mark a bill paid. Require a successful receipt and
   matching token, chain, sender, recipient, exact amount and finality. Testnet mirrors
   never clear real local-currency liabilities.
5. **Pass release validation.** Lock the hardened package version; run application
   regressions plus separately authorised testnet integration; exercise provider
   failures, worker crashes, replay, missed events, restart, update and backup
   restoration. Review secrets/recovery custody, MFA, monitoring, alerts and rollback
   procedures before any controlled mainnet decision. No mainnet payment or custody
   migration is implicit.

## Settlement verdicts

Only `verified` means money moved — and only after successful execution in a committed
block with matching sender, recipient and amount. Every other verdict keeps
`settled: false` and `fabricated: false`; an unreadable chain is *unresolved*, never
evidence of wrongdoing.

| Verdict | Means | What it proves |
| --- | --- | --- |
| `verified` | A receipt exists and reports success | The chain executed it — not that it moved the intended amount |
| `reverted` | A receipt exists and reports failure | Chain-proven failure — the only absence-free verdict that fails a row |
| `pending` | Known to the chain with no receipt yet | Still in flight; nothing is concluded |
| `unresolved` | No transaction with this hash was found | An open question, never a failed payment |
| `observed` | Provider reports completion, no receipt readable | Provider claim only |
| `unverifiable` | Neither chain nor provider readable | No evidence available |
| `ledger_only` | No hash recorded | A local ledger row that never claimed a receipt |

A missing RPC result alone does not prove fabrication or failed settlement:
propagation delay, a reorganisation, and a hash from another network all look identical.
Keep uncertain outcomes unresolved and reconcile without blind resubmission. Fake-driver
receipts are simulated, never on-chain proof.

```bash
php artisan lepton:reconcile
php artisan lepton:reconcile --fix   # marks only chain-reverted receipts failed
```

## Arc-specific facts the code encodes

- On Arc, USDC is the gas token — but a Circle **agent-wallet** transfer is relayed and
  Circle sponsors the gas: the payer's balance delta equals the principal exactly. So
  affordability is `amount <= balance` (not `amount + fee <= balance`), and a receipt
  fee above the payer's ceiling must never refuse a settlement.
- Agent-wallet transfers are asynchronous: without `--quiet`, `circle wallet transfer`
  returns a fee preview and does not broadcast; with `--quiet` it returns a Circle
  transaction id (a UUID), not a `0x…` hash.
- Decimals come from the log emitter, never the payload shape; the payer appears only as
  the `from` topic of a Transfer log (relayed receipts show a different `tx.from`).
- Arc has deterministic finality — receipts are immediately authoritative; confirmations
  = 1, no reorgs. The block read is corroborating evidence and must never gate
  settlement.

## Release safety

Preview builds publish only after successful same-repository push CI, from its exact
commit, and use `preview`/version/SHA tags — never stable `latest`. Manual releases
require successful CI for the dispatched `main` commit, reject existing tags, and reject
`latest` for drafts/prereleases. Configure required reviewers on the GitHub `release`
environment before official publication; an environment name alone does not enforce
approval.

Before going live with any funds, know what is still missing from the target lifecycle:
reservation release/funding rollover, approval renewal/withdrawal and factor recovery,
local-to-testnet mapping authority, durable outbox/attempt recovery, execution recovery,
and matching settlement verification. A draft, policy activation or developer demo is
not a certified school treasury system.
