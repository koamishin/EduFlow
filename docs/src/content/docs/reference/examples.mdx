These examples are for contributors. They intentionally do not sign or submit a
payment. Use the application's reviewed lifecycle rather than calling a transfer
gateway from a new controller or one-off script.

## Parse an exact amount

`Money` is the application's DTO. Its decimal input is a string with the currency's
supported precision:

```php
use App\DTOs\Money;
use App\Enums\CurrencyCode;

$amount = Money::fromDecimal('45.125001', CurrencyCode::USDC);

$amount->toBaseUnits(); // 45125001
$amount->decimal(); // "45.125001"
$amount->jsonSerialize();
// ["minor_units" => "45125001", "currency" => "USDC", "decimal" => "45.125001"]
```

Do not multiply a float by a million and cast it back to an integer. Formatting or
chart values are not the authoritative stored amount.

## Format a stored aggregate

```php
use App\DTOs\Money;

Money::formatExact('45125001', 'USDC'); // "45.125001 USDC"
```

The helper also supports string aggregates beyond a single `Money` integer. Malformed
input returns an unavailable message instead of guessing a plausible amount.

## Inspect a gate without creating authority

```php
$submissionEnabled = (bool) config('eduflow.submission.enabled', false);
$newSubmissionsStopped = (bool) config('eduflow.submission.stop_switch', false);

$automaticBridgeEnabled = (bool) config('eduflow.autonomous_pipeline.enabled', true);
$bridgeMayDisburse = (bool) config('eduflow.autonomous_pipeline.auto_disburse', true);
```

These are observations, not an `isSafeToPay()` implementation. Approval evidence,
current funding, correct rail, stop controls, and recovery identity must still be
validated by the existing services. The bridge can override submission configuration
in-process and not every direct caller checks its enabled flag.

## Never infer settlement from transaction visibility

This predicate is insufficient and must not be used:

```php
// Incorrect: an array says nothing about success or the expected movement.
$settled = is_array($transaction) && $transaction !== [];
```

Use the dedicated verifier and reconciliation path with the original expected payment
evidence. A hash lookup, provider `COMPLETE`, or webhook delivery alone is not that match.
Do not write a new simplified settlement shortcut around them.

## Learn from integration tests

Read these real fixtures and negative cases before adding a path:

- `tests/Feature/TuitionToVendorWorkflowTest.php`: receipt, reviewed plan, payment approval,
  single submission, and mocked matching settlement. The ordinary path leaves the source
  invoice pending in this test.
- `tests/Feature/StudentTuitionConsentRecoveryTest.php`: consent and recovery behavior.
- `tests/Feature/StudentBillPaymentProcessorTest.php`: the separate incoming bill lane.
- `tests/Feature/CircleWebhookTest.php`: notification containment and deduplication.

Provider and chain stubs prove application behavior under those inputs. They are not
evidence that a live provider integration or a school rollout succeeded.
