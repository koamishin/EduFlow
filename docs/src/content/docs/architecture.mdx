OpenSinop is one Laravel application with multiple interfaces, not separate finance
microservices. Its HTTP routes, staff panels, jobs, and commands share the same domain
records and installation context.

## System at a glance

```text
Browser
  Staff panels: Filament / Livewire
  Student and policy pages: React / Inertia
          |
Laravel actions and services
  Collection evidence · planning · reviews · payment processing
          |
Database and private files       Queues and scheduler
          |
Payment transports and Lepton gateways
          |
Circle provider requests and Arc Testnet observations
```

The static handbook in `docs/` is a separate Astro/Starlight build. It does not run
Laravel, connect to the database, or host a payment endpoint.

## Interfaces

- `routes/web.php` serves Inertia pages and authenticated finance endpoints.
- `AdminPanelProvider` registers `/admin` for installation/accounts and records.
- `FinancePanelProvider` registers `/finance` for collections, supervision, payment
  approvals, treasury, and selected resources.
- Student pages bind the signed-in student's account rather than accepting arbitrary ownership IDs.

Menu visibility is not authorization. Actions and services perform server-side checks;
inspect the applicable policy before changing a route or reusing an action.

## Evidence before authority

The ordinary finance path is organized around records that keep their reviewed content:

1. `CollectionBatch` and its review record what was received and independently checked.
2. `InvoiceVersion` and its review preserve exact source bill evidence.
3. `BudgetSnapshot` binds a selected bill set, allocation, cash, commitments, and receipts.
4. `FinanceWorkflowRun` stores a planning result; `FinancePlanReview` records staff judgment.
5. `PaymentIntent`, funding evidence, and `PaymentReservation` bind an exact proposed send.
6. `PaymentAuthorization` records the normal reviewer decision and credential evidence.
7. Outbox and attempt records retain submission identity through provider uncertainty.
8. Settlement reconciliation checks the expected movement before recording verified results.

Digests detect content drift. They do not independently authenticate a source document
or prevent a database administrator from rewriting all content and fingerprints.

## Payment transport is asynchronous

`CircleAgentWalletTransport` returns a provider handle on acceptance and later resolves
it to a transaction hash. It has an HTTP agent-wallet path and CLI fallback; do not
describe every operation as spawning `circle`.

The dedicated executor accepts already bound submission work. The verifier, not the
executor or a notification, determines whether matching movement settled. Tuition
and campus-bill processors have their own consent, recovery, and posting paths.

`CircleRestGateway` is a different developer-wallet integration. Current payment
transport execution refuses it pending reviewed payer-fee controls; an API key is not
automatic access to existing agent wallets.

## Background processing

Planning and policy evaluations use Laravel's default queue connection/queue in the
current dispatchers. Payment jobs use configured named queues and connections. The
scheduler dispatches/reconciles work under separate flags.

The app uses Octane in the image. Do not place request-specific state in shared
singletons or statics. Changes to cached settings or code need the appropriate
long-lived processes restarted.

## Experimental and legacy paths

`AutonomousPipelineBridge` reuses finance actions but selects reviewer identities,
may grant permissions, generates TOTP inputs, enables submission in-process, and can
mark invoices paid. It is not equivalent to independent staff authorization.

The legacy `EduFlowAgent` invoice/assistance cycle is also different from the reviewed
vendor path. Preserve the distinction in tests, documentation, and UI claims. See
[Current limits](../institution/safety-readiness/) for the operating boundary.
