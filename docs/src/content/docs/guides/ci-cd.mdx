title: Releases and docs publishing
description: How application checks and release jobs differ from the automatic GitHub Pages workflow for this handbook.
---

The application release and the documentation website are separate builds.
A successful handbook deployment does not test payment readiness or release a new
application image.

## Application checks

`.github/workflows/ci.yml` runs PHP style, static analysis, Rector checks, frontend
linting, TypeScript, and backend/browser tests for its configured branches and PRs.
Read the workflow for the current matrix and installed tool versions.

The preview release workflow waits for successful same-repository push CI and checks
the tested commit's provenance. Preview image tags do not automatically replace stable
`latest`. Manual official releases have separate version, tag, and CI checks.

Required reviewers on a GitHub environment must be configured in repository settings;
an environment name alone does not enforce independent approval.

## Container runtime is not every service

The image includes FrankenPHP/Octane and Supervisor configurations. Default HTTP mode
starts the web process and optional installed monitoring programs, not the general
queue worker or scheduler. Shipping their config files is not the same as running them.
Use [Operations](../operations/) for background setup.

## Publish this handbook

`.github/workflows/docs.yml` builds Astro/Starlight in `docs/`, checks internal links,
and publishes `docs/dist` to GitHub Pages.

| Event | Result |
| --- | --- |
| PR to `main` changing `docs/**` or the workflow | Build and link validation only. |
| Push to `main` changing those paths | Build, validate, and publish. |
| Manual run on `main` | Build, validate, and republish. |
| Manual run on another branch | Build only; cannot replace the published site. |

The repository's Pages source must be **GitHub Actions**, not branch publishing of raw
MDX. This handbook is static; it needs no Laravel server, school database, or provider
credentials in the workflow.

## Preview a change locally

Use the locked Node requirement (`>=22.22.0` for the current Astro version):

```bash
cd docs
npm ci
npm run build
npm run check:links
npm run preview -- --host 127.0.0.1
```

Open the printed preview address under `/OpenSinop/`. The project uses that base for
`https://koamishin.github.io/OpenSinop/`. Custom-domain moves need both site/base
configuration and updated link-check configuration.

## Write a useful guide

Keep the reader's task ahead of the implementation:

1. Say who the page is for and what they will accomplish.
2. State prerequisites and current operating limits before any command that can change records.
3. Use the exact screen labels or verified command options.
4. Explain the expected result and the next step.
5. Move model names, schemas, and deep details into developer reference.

Pages live in `docs/src/content/docs/`. Existing URLs are kept where practical; add a
sidebar entry for a new guide. Prefer Starlight's built-in components over a new UI
dependency. Use sentence-case headings and short, complete explanations.

## Links and verification

Content links must work under `/OpenSinop/`. Starlight's sidebar uses the configured
base, but content links are not automatically rewritten. Relative links work for
ordinary directory pages; a custom 404 must use base-aware links because it can be
served at an arbitrary missing URL.

`npm run check:links` checks the built output. Tests also protect link resolution and
key factual boundaries. The app's Vite-Plus check excludes `docs/**`; that separation
does not exempt the handbook from its own build and tests.
