## Application pipelines

| Workflow | Trigger | Purpose |
| --- | --- | --- |
| `.github/workflows/ci.yml` | push/PR to `main`, `develop`, `master`, `workos` | Pint, PHPStan (8.5), Rector dry-run, Pest (backend + browser groups, Node 22, Playwright Chromium), Vite-Plus frontend check |
| `.github/workflows/auto-release.yml` | successful CI run on push to `develop`/`main` | Validates CI provenance, checks out the exact tested SHA, resolves a preview identity, builds the multi-arch FrankenPHP image and pushes a **preview** release (never `latest`) |
| `.github/workflows/manual-official-release.yml` | manual `workflow_dispatch` on `main` | Official release: version/tag validation, refuses existing tags and rejects `latest` for drafts/prereleases, promotes the image, updates `version.json` |
| `.github/workflows/docker-latest.yml` | manual `workflow_dispatch` | Ad hoc Docker build check only — never publishes |

Release safety rules encoded in these workflows:

- Only successful **same-repository push** CI may publish a preview, from the branch head
  that CI actually tested (an obsolete run for a newer head is refused), and the CI
  workflow path is verified against the trusted `.github/workflows/ci.yml`.
- Preview images use `preview` and version/SHA tags; `latest` is reserved for official
  releases from `main`.
- Configure required reviewers on the GitHub `release` environment before official
  publication; an environment name alone does not enforce approval.

## Docker architecture

The production image is multi-stage:

1. **Vendor stage** — `composer:2.8` installs PHP dependencies with an optimised
   classmap (no dev, no scripts).
2. **Assets stage** — `oven/bun:1` builds the frontend via Vite (Wayfinder generation
   included).
3. **Runtime** — `dunglas/frankenphp` (1.9) + `laravel/octane`, managed by Supervisor:
   FrankenPHP/Octane web server, queue worker(s), scheduler, plus optional Horizon/Pulse
   configs (`docker/supervisord.*.conf`) when those packages are installed.

Related files: `docker/Dockerfile`, `docker/Dockerfile-Dev`, `docker/start-container`
(the image entrypoint), `docker/run.sh`, `docker/healthcheck`, `docker/nginx.conf`,
`docker/php-fpm.conf`.

The runtime stage bakes identity defaults as build arguments — `APP_NAME=OpenSinop`,
`APP_ENV=production`, `APP_DEBUG=false`, `APP_URL=http://localhost:8000` — and sets
`CONTAINER_MODE=http`, so a stock build never points at someone's production URL. Pass
your own values (`--build-arg …` in `docker/run.sh`, or the `environment:` block in
Compose) for a school deployment.

`docker-compose.yml` runs the published image (`ghcr.io/koamishin/opensinop`) with
PostgreSQL 16 and Redis 7 and four named volumes (`opensinop_db`, `opensinop_storage`,
`opensinop_cache`, `opensinop_redis`). See [Installation](../../getting-started/installation/).

## This documentation site (GitHub Pages)

The docs in `docs/` are an Astro + Starlight site. `.github/workflows/docs.yml` builds
and publishes it to GitHub Pages:

```yaml
on:
  push:
    branches: [main]
    paths: ['docs/**', '.github/workflows/docs.yml']
  pull_request:
    branches: [main]
    paths: ['docs/**', '.github/workflows/docs.yml']
  workflow_dispatch:
```

- **build** — Node 22, `npm ci` in `docs/`, `npm run build`, then upload `docs/dist` as
  the Pages artifact. Runs on pull requests too, so docs changes are validated in CI.
- **deploy** — runs only for pushes to `main`; publishes the artifact to the
  `github-pages` environment via `actions/deploy-pages`.

Enable it once in the repository: **Settings → Pages → Source: GitHub Actions**.

### Running the docs locally

```bash
cd docs
npm install
npm run dev       # dev server
npm run build     # static build to docs/dist
npm run preview   # serve the built site
```

`astro.config.mjs` sets `base: '/OpenSinop'` for the GitHub Pages project site
(`https://koamishin.github.io/OpenSinop/`). For a custom domain or a user/organisation
site, set `base: ''` (and update `site`). `npm run preview` then serves the site under
`/OpenSinop`.

### Writing a docs page

Pages are MDX in `docs/src/content/docs/`, with Starlight frontmatter:

```mdx
---
title: Page title
description: One-sentence summary used for SEO and social cards.
---

import { Aside } from '@astrojs/starlight/components';

<Aside type="caution">A short, prominent warning.</Aside>
```

Useful Starlight components: `Card`/`CardGrid`, `Aside`, `Tabs`/`TabItem`, `Steps`,
`Badge`, `FileTree`, `LinkCard`, `Icon`, plus fenced code blocks and GitHub-flavoured
Markdown. Broken internal links fail the build. The `docs/` site is independent of the
application's `package.json` (the app pins Vite-Plus; Astro brings its own toolchain) —
never merge the two dependency trees.
