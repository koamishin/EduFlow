Start with [Local setup](../../getting-started/local-development/) and the
[project map](../directory-structure/). Prefer a focused change with evidence over a
large rewrite that changes financial behavior and presentation together.

## Before changing code

Read `AGENTS.md`, `.ai/rules/index.md`, the matching area rules, and nearby tests.
Verify the installed package version before choosing an API. Rules and old prose can
drift from the code; investigate contradictions instead of copying them as fact.

For a finance path, identify who supplies evidence, who reviews it, what can call a
signer, and how uncertainty is recovered. The ordinary reviewed path, legacy demo,
student consent paths, and automatic bridge are not interchangeable examples.

## Run the checks that match your change

From the application root:

```bash
npm run check
npm run types:check
composer test:lint
composer phpstan
composer rector
php artisan test --compact --filter=NameOfAffectedTest
```

`composer rector` is a dry run; `composer lint` fixes PHP style. Use the package and
project rules for broader checks before merging. Browser tests require their installed
Playwright support, not a production browser session.

## Test money and authority boundaries

Use exact strings/units and explicit fakes. Cover changed evidence, wrong ownership,
expired approvals, invalid factors, duplicate identities, uncertain provider outcomes,
and queue retries. An existing request must not become a blind second transfer.

Do not run live transfers, seed school data, or call OTP login from tests. A chain stub
can prove the application's matching logic under those facts; label it honestly.

## Document actual behavior

Walk the code path before writing a guide. Use screen labels for staff pages and put
class names in developer reference. Separate implemented behavior from desired safety
properties, particularly where an experimental path bypasses ordinary human interaction.

To check this handbook, run in `docs/`:

```bash
npm run test
npm run build
npm run check:links
```

Also inspect the rendered pages at desktop and mobile widths, in both themes. A
successful static build proves neither readability nor application payment safety.

## Submit a focused PR

State the behavior changed, evidence inspected, tests run, and remaining limits.
Exclude secrets, personal/student data, provider sessions, and private source documents.
Do not remove audit history or weaken financial checks to make a demo pass.
